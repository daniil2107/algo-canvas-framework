# Decompose a paper for Algorithm Canvas

Start from the actual paper. Prefer the supplied LaTeX, PDF or code when resolving equation numbers and pseudocode. Read figure captions and experimental conditions when a design choice depends on a measured result.

1. Use `read_canvas({})` for the current revision, problem, setting and existing stages. If the existing objective and setting are both blank, derive the objective and setting from the paper. On the first import, include both strings as `problem: {objective, setting}` in the same `apply_research` call as the paper records. The objective must be nonempty. If either root field already contains text, reuse that root and omit `problem` from the call. If the paper addresses a different problem, describe the mismatch before proposing a merge. Reuse existing IDs for matching stages and insights.
2. Use [atomic decomposition](../atomic-decomposition/SKILL.md) for the operations that need a line-level contract. Follow the paper's actual control flow. For each meaningful line or group of lines, record its inputs, operation, outputs and purpose. Preserve dependencies, loop bounds, conditionals, and the distinction between an algorithmic step and a setting used only in an experiment. Include the originating algorithm, line, equation or section in the stage description or supporting evidence. For explicit control flow, include `flow: [{id,from,to,condition}]` in the same import. Use guards on branches and loops and reuse the stages’ IDs. On an empty canvas these arrows specify the entire flow. On an existing canvas supply only intended new arrows.
3. Extract the problem properties each step exploits as insights with `text` and `basis`. A limit or a goal that the objective or the setting already states is not an insight: cite it with the reserved id `objective` or `setting` in `because` or `uses`, and say which part in the stage’s `job` or the block’s `why`. Set the stage’s `job` to its role in the objective and `because` to insight IDs. For the paper's own block, describe its mechanism in `does`, rationale in `why`, linked insight IDs in `uses`, and the tradeoffs or missing assumptions in `costs`. Distinguish the authors’ explanation from your inference. An ablation of a component supports that component only at the tested settings.
4. Capture a specific result used as evidence as an addressable result in a card. A paper title or URL alone cannot serve as a saved block’s evidence. To import a new card, use `cards` in `apply_research` with an unused ASCII slug for `id`, a short `title`, `source`, `where`, `assumptions`, `passage` and `wording` (`quoted` or `paraphrased`). A block may use `cardId` such as `theory/imported/variance-bound.md#R1`. Import the card and referencing records together.
5. If the user requested canvas changes, submit one append-only `apply_research` call with the latest `rev` and the new insights, stages, sourced blocks and cards. Match its argument schema. Each new stage needs a distinct ID, name and job. The server marks new blocks as suggestions, including a published block awaiting adoption. Preserve existing selections and versions. On a stale revision, reread, deduplicate and retry with the remaining changes. For a read-only request, present the decomposition inline.

Report which stages came directly from the paper, the assumptions the source leaves open, and the IDs or locators the user can inspect.
